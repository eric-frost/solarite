# Changelog

All notable changes to Solarite are documented here. This project follows [Keep a Changelog](https://keepachangelog.com/) and [Semantic Versioning](https://semver.org/). While the version is below 1.0, minor releases may include breaking changes; these are called out below.

## [Unreleased]

### Changed
- **Breaking:** `h()` and `toEl()` return a `DocumentFragment` for every template that has an expression at its top level, beside its nodes rather than inside one of them, such as ``h()`Total: ${n}` ``, ``h()`<h1>Fruit</h1>${rows}` `` or ``h()`${icon} <b>Save</b>` ``.  That holds when only one node is written beside the expression, and when the expression draws nothing.  They used to return that one node, a `Text` or an element, without what the expression drew: ``h()`Total: ${n}` `` gave the text `Total: ` without the number, and ``h()`<h1>Fruit</h1>${rows}` `` the heading without its rows.  The same went for a component, an svg element or a table row with an expression beside it, and for precompiled JSX such as `<><h1>Fruit</h1>{rows}</>`, and `Solarite-debug.js` stopped at an assertion for the first of these.  The `render()` of an object given to `toEl()` now updates such a template where it was put; it threw, or put the rows before the heading.  Code that used the result as an element, to give it a class, remove it later or keep it to render into again, must write the template inside one element, as in ``h()`<p>Total: ${n}</p>` ``.  The delegated handlers of such a template are served by the page's document, as those of any template with several top-level nodes are: they don't run in an element that isn't in the page, in a closed shadow root or in an iframe's document, and their `this` is the fragment instead of the element.  A `<style>` inside its one element is no longer scoped to that element either: `:host` in it is left as written instead of being rewritten to match the element.  A template whose top level is one element or one component, with only white space or comments around it, still returns that element or component.
- **Breaking:** a child component's `render()` gets a function, `hasChanged()`, as its second argument instead of the `changed` boolean.  It compares the attributes only when called, so a child that never asks no longer pays for a comparison on every render of its parent.  That comparison serializes the attributes and took about 5ms for 10,000 rows.  Write `render(fields, hasChanged=() => true)` and `if (!hasChanged()) return;`.  Code that still tests `if (!changed)` renders correctly but never skips, since a function is always truthy.
- **Breaking:** `Globals.reset()` is gone.  It had done nothing since 2024, so nothing can have depended on it.
- **Behavior change:** an element moved out of its list row (not the whole row, an element inside it) no longer keeps its delegated handlers; a `native:` handler does.
- **Behavior change:** a list row finds the elements that have a delegated handler by their places in the row's template when an event or a changed value first needs them, and keeps them, instead of finding them when the row is drawn.  So a node that other code puts into the row in front of such an element before then, such as a tooltip inserted right after the element it belongs to, can make the handler run when that node is clicked and not when its own element is.  A row that holds an `<input>`, `<select>`, `<textarea>` or `contenteditable` element still finds its elements when it is drawn, so the icons password managers and autofill tools put beside form controls move nothing.  It comes with the faster list building below.  Event Delegation in the documentation says how to write such rows.
- **Behavior change:** in a list that also holds a raw DOM node, a row whose update throws part-way (an event attribute given something that isn't a function, an attribute function that throws) leaves every one of its delegated handlers with the old item until the next render.  In 0.9.0 the handlers the update had reached received the new item and the rest the old one, exactly as with `eventDelegation: false`, which is still what happens in a list without a raw node.  It comes with the faster list building below, which keeps a row's delegated handlers in its template.
- **Behavior change:** in an `h.map()` list without keys, removing one run of adjacent items now removes the elements those items were drawn in.  Rows whose values were identical used to be matched by position, so removing the first of three identical rows dropped the last element, and anything typed into the rows moved up by one.  Removing items in two separate places in one render still matches identical rows by position; give rows a `key` when their elements hold state.
- **Behavior change:** an empty template (``h(el)`` ``) rendered into an element that already has children sets them aside instead of discarding them, and they go to the slots of the next template rendered into the element, or to its end.  Rendering the empty template a second time no longer removes what other code has put into the element in between.
- **Behavior change:** a template that is only text (``h(el)`Name` ``) rendered into an element that already has children puts the text before them, as every other template does.  It used to be put after them: a `<label>` holding an `<input>` showed the input first and now shows the text first.  The same goes for a component whose template is only text and the children the page's html gave it.
- **Behavior change:** an event attribute with text beside its handler, such as `onclick="${f} "` with a stray space, throws `Solarite: onclick="...${...}..." mixes a handler with text.`  The handler used to be called while rendering, and what it returned was installed as an inline handler.
- **Behavior change:** a `<script>` in a template runs only when it has no `type` or a JavaScript type, as the browser would run it.  A `type="application/ld+json"` block used to be run as code, which made the render throw, and `module` and `text/template` scripts were run too.  A script that runs now runs once its template's expressions are written, so `<script>window.user = '${name}'</script>` sees the name; it used to run before them, with empty text where each `${...}` was.
- Long lists build and clear faster.  A new row is cloned with its text already in place instead of being filled in afterward, and the row's delegated handlers stay in its template rather than being written onto the elements that carry them; the event dispatcher finds the row on the event's path and reads each handler from the row's template when that handler's turn comes.  Both changes mean nothing below the row's root element is touched while the list is built, which was most of the per-row cost, and the browser has correspondingly less to tear down when the list is cleared.
- The loops that build, keep and place the rows of a list are small functions of their own instead of sections of two large ones.  A JavaScript engine decides what to compile one function at a time and in proportion to how much of that function has run, so a loop inside a large function that runs once per render stayed in the slowest tier through a whole list; on its own it is compiled within the first few hundred rows.
- Updating and removing rows of an `h.map()` list does less work.  A row rewritten in place writes into the text node it already has.  A list that lost one run of adjacent rows (a deleted row, a deleted selection, a list cut short) is settled by comparing the old and new items from both ends, so only the rows that left are visited.  A keyed list whose rows were all replaced, such as the next page of a table, skips the per-row matching it used to do first.
- Handling an event does less.  The temporary listeners the dispatcher attaches for an event are removed when the event has reached the last element it has a handler on, instead of by a timer task afterward; if a handler stops the event before that, they stay until the next event of that type.  The dispatcher no longer searches every element on the event's path through its whole prototype chain for a handler, and adds no property to the event.
- A parent's render no longer copies each array it gives a child component as an attribute.  `<my-table rows=${rows}>` with 10,000 rows copied the array, about 2 microseconds, on every render of the parent.
- The comparison behind `hasChanged()` is about twice as fast for plain data.  It hands plain objects and arrays to the browser's own `JSON.stringify()`, and keeps the slower path, which writes ids for functions, elements, and repeated or circular objects, for arguments that hold them.  Both give the same result.
- The Brotli download grew from 12.7KB to 15.0KB.

### Fixed
- Text that is alone in its element, such as `<span>${name}</span>`, or written straight inside the tag of a custom element that doesn't render through Solarite, such as `<sl-button>${label}</sl-button>`, shows every new value after the browser's page translator has replaced it, and keeps its translation while its value stays the same.  Chrome's translator swaps each piece of text for a `<font>` element, so new values were written to a node that was no longer on the page and the old translation stayed, and when such text changed to a template both were shown, in list rows as well.  The new "Page Translation" section of the documentation says how to write templates that stay correct on a translated page.
- An `h.map()` whose callback returns plain strings no longer shows the wrong text after items are inserted, removed or reordered.
- A list drawn by `h.map()` that was replaced by a plain string or number, or by rows that are arrays or raw DOM nodes, and then drawn again from the same items, now shows those items again instead of keeping what replaced them.
- A row that throws while it is created (an event attribute given something that isn't a function, a component whose constructor fails) no longer leaves a half-drawn list that the next render draws a second copy of, and no longer leaves a long keyed list's parent element out of the document.  The error still reaches the caller; the list is left empty and the next render draws it whole.
- When a component in a row of an `h.map()` list throws as it renders, the rows the same render had updated before it are drawn right by the next render, also when the app goes back to the items they showed before.  They used to keep showing the newer items.
- A template whose `data-id` would overwrite a property of the element, such as `data-id="title"`, or whose `<script>` throws, no longer leaves its half-built elements in the element.  The next render took them for the element's slot children and showed them inside its own `<slot>`, a template wrapped in a component's tag left the attributes it had copied onto the component, and a component declared inside another template lost the children written inside its tag.  The error still reaches the caller, and the element is left holding only the children it was given, so the next render draws into it as into an element never rendered.
- A list whose first row has no key, such as a heading, a plain string or a row an `h.map()` callback hides by returning `null`, follows the keys of the rows after it, and so does a keyed list that also holds a DOM node, such as a spinner beside the rows.  Their elements used to be handed to other keys as soon as rows changed places, so what was typed into one row's input showed up in another's, and a keyed row removed from such a list could leave its element to a new key.
- A list row keeps the elements its events and updates have found, and finds its other elements from them, so a node other code puts into the row in front of an element it has found no longer makes a later update write into the wrong element.  Such an update used to write the new value into another element of the row.
- An `h.map()` callback that renders its own host again no longer leaves one item drawn twice and another missing.  It happened in a list without keys when rows were inserted or changed places in the same render: the render the callback started had reused rows for other items, and the render it interrupted went on from what it remembered of them, and the wrong rows then stayed until the items changed.  The interrupted render now notices and starts the list over, so the list it was given is the one shown.  The same holds when the nested render empties the list or puts plain text in its place, which could leave a second copy of the rows.
- A row of a keyed list that is a plain string, such as a separator between keyed rows, keeps its text node while it shows the same text and the list changes only before it or only after it.  A keyed list given as an array used to remove and recreate the text node of every such row on each render.
- A listener added with `addEventListener` that dispatches another event of the same type through its own element no longer costs the first event that element's template handler.  The handler used to run for the second event only.
- An event whose handler dispatched another event of the same type that was stopped now removes its temporary listeners when it ends.  They used to stay, with the stopped event's, until the next event of that type.
- A keyed `h.map()` list that also holds a row without a key no longer throws `NotFoundError` when, in one render that keeps the list's length, more than eight of its rows get new keys and a row that stays ends up at another position.  The row without a key was removed and then used as the place to insert the next row.
- An event handler on a plain element such as `<i>`, `<em>` or `<section>` no longer counts as a live property, which had made every row of such a list be rewritten on every render.
- One `Event` object dispatched a second time now runs delegated handlers the second time as well.  It used to be skipped when both targets sat at the same depth.
- Handlers of click, input and the other delegated events in a template made by `h()` or `toEl()` with several top-level nodes, such as two buttons made by one `h()` call and appended to the page, now run.  They never did unless something else on the page handled the same type of event through Solarite, because the listener was registered on the inert document the template was built in instead of the page's.
- `onfocusin` and `onfocusout` attributes bind their handlers like every other event.  Elements have no property of those names to detect the event by, so the attribute was treated as an ordinary one: the function was called while rendering and its result written as the attribute's text.  The touch events (`ontouchstart`, `ontouchmove`, `ontouchend`, `ontouchcancel`) had the same problem on a machine without a touch screen.
- A string given to an event attribute that is bound when the template renders (`onfocus`, `onscroll`, `native:onclick`) throws in a list row as it does everywhere else.  In a row it was written as an ordinary attribute instead, so the browser ran the string as code when the event fired.
- A string of whole attributes, such as `<div ${'title="Hello" hidden'}>`, is applied again in the minified build.  Since 0.8.0 `Solarite.min.js` wrote none of them, and a child component given such a string received none of those attributes: the minifier had removed the code that reads the string.  The unminified build was not affected.
- Whole attributes given as a string keep names that hold a colon, a dot or an `@`, such as `xml:lang`, `x-on:click.prevent`, `hx-on:click` or `@click`.  `<div ${'x-on:click="go()"'}>` used to get two attributes, `x-on` and `click`.
- An empty `value` on a `contenteditable` element, as in `<div contenteditable value=${text}>` with `text` set to `''`, `null`, `undefined` or `false`, empties the element.  It used to keep what it showed, so an element that was reused, such as a grid cell moved to an empty column, went on showing its old content.
- `null` and an empty string turn a boolean property such as `disabled`, `required`, `multiple`, `open` or `selected` off, as `false` does.  `disabled=${this.busy || null}` used to disable the button whatever `busy` was, because the empty attribute written with it turned the property back on.  `value=${null}` still clears an input.
- `muted` and `volume` on a `<video>` or an `<audio>` set the properties they name.  A render used to write them only as attributes, so the video stayed unmuted at full volume.
- An `h.map()` callback may return an array, a DOM node, a nested list, a number, `null` or nothing for any item.  This used to work only when the first item's result was of that kind; for a later item it threw, and `null` threw for the first item too, so a callback that hid a row by returning `null` could not be used.
- An `h.map()` that is inside an array, returned by a function, or returned by the callback of another `h.map()` takes the same callback results as one written straight into the template.  It used to throw `Invalid value used as weak map key` or `Cannot read properties of null (reading 'key')` for anything but a template or a string, so a list of groups whose inner callback hid an item by returning `null` could not be drawn.
- A list whose rows have more than one root element, such as a `<dt>` with its `<dd>`, shows each row whole when it brings back rows it had taken out: after a DOM node was shown in the list's place or beside it, for instance a spinner element while the rows load; after a row threw in a list that also holds a DOM node; and after a row threw while it was created, in the render that removed such rows.  Each such row used to come back as its first element only, or behind the content that follows the list, and a later render could throw `Cannot read properties of null (reading 'nextSibling')` and remove whatever followed the list in the same parent, after which that template threw on every render.  A row that throws in a list holding a DOM node leaves the rows that were shown as they are, the error still reaches the caller, and the next render draws the list it is given.
- A DOM node used as a child in a template is shown again when that template comes back after being removed: an item filtered out of a list without keys and back in, or a node shown in one of two templates by turns.  The template's elements were kept for reuse while the node had been moved elsewhere, and came back empty.
- A JSX fragment (`<>...</>`) keeps its elements when it is rendered again.  In the setup that needs nothing extra installed (a tool's built-in JSX setting, or `h` as the JSX factory), each render took the fragment for a template it had never seen, so everything inside it was removed and built again: an input lost its focus and what had been typed, a child component was constructed again, and every discarded copy stayed in memory for as long as the template around the fragment was in use.  JSX precompiled by Deno or by the Vite, esbuild and Babel plugins was not affected.
- An array whose first item is an object and whose second is `null`, `undefined` or `false`, such as `[item, null]`, is no longer taken for a two-way binding path.  Given to a child component as an attribute, the component received `undefined` instead of the array; given to an element, as in `<input value=${[item, null]}>`, typing wrote a property named `null` onto the object.
- A customized built-in, a component written as `<p is="my-text">` rather than `<my-text>`, that is rendered before its class is defined is now built as soon as `customElements.define()` is called, as a component with a tag of its own already was.  It used to stay an empty placeholder, with none of its expressions passed to a constructor, until something rendered its parent again.
- `toEl()` and `h()` given a template whose only node is a component, such as `<my-comp count=${1}></my-comp>`, return the component, constructed with its attributes and given its children.  They used to return a lifeless element named `my-comp-solarite-placeholder` and never constructed the component, which only happened when it had another node beside it or an element around it.  The same holds for a component written as `<p is="my-text">`.
- A component whose tag name holds `_` or `.`, such as `<my-tag_x>` or `<my-el.v2>`, is constructed.  It used to stay in the page under a placeholder name, and its constructor was never called.
- In `Solarite-debug.js` a template of one element with an expression commented out beside it, as in `<b>${x}</b><!-- ${y} -->`, no longer stops at an assertion.
- `Solarite-debug.js` no longer warns "Unkeyed item in a keyed list" for a row that is a plain string, or that an `h.map()` callback hid by returning `null`.
- A `<` written straight before an expression, or as the last character of a template, is text, as it is to the browser.  A template such as `${min} <${max}`, or a plain string such as `h('a <')`, used to throw `Cannot read properties of undefined (reading 'match')`.
- A template of plain text with no element to render into, such as ``h()`Hello` `` or ``toEl(h`Hello`)``, returns its `Text` node, as `toEl('Hello')` does.  It used to throw `Text node needs an element.`
- Rendering into a `DocumentFragment` or a shadow root no longer throws `Cannot read properties of undefined (reading 'includes')` when the template has exactly one root element, such as `<div>...</div>`.  A template with several root elements, or with text beside them, already rendered there.
- An html comment in a template may hold an apostrophe, a quote or a `>`.  A comment such as `<!-- don't -->` used to make the whole template throw `Solarite: bad html or duplicate attribute` when an expression came after it, because the apostrophe was read as the start of an attribute value.  So did an expression commented out after a `>`, as in `<!-- a > b ${x} -->`, and a conditional comment with expressions in it.
- An expression inside `<?x ...?>` no longer makes the template throw `Solarite: bad html or duplicate attribute` in Chrome, which now reads it as a processing instruction rather than a comment.
- An attribute value written without quotes may hold an apostrophe or a quote, as in `<p title=don't>` or `<a href=/search?q=it's>`.  It used to be read as the start of a quoted value that never ended, so a template with an expression anywhere after it threw `Solarite: bad html or duplicate attribute`.  The same goes for a quote inside `<!...>` or `</ ...>`, which the browser reads as a comment that ends at the first `>`.
- An unquoted expression straight before the `/>` of a tag, as in `<input oninput=${f}/>` or `<circle r=${5}/>`, ends there, and the tag closes itself.  The browser read the slash as part of the value, so a handler written so was called on every render and what it returned was installed as an inline handler, and a value gained a slash: `<circle r=${5}/>` drew nothing.  A slash meant for the value goes inside quotes, `href="${base}/"`.
- A private-use character in a template's attributes or comments, where icon fonts put their glyphs (`data-icon="&#xe600;"`, `placeholder="&#xf002; Search"`), no longer makes the template throw `Solarite: bad html or duplicate attribute`, with or without expressions in it.
- The text of a `<script>`, a `<style>` or a `<textarea>` is no longer read as html.  A `<` before a letter in it, as in `if (a<b)` or `@media (400px<width)`, used to be taken for the start of a tag that ran to the next `>`.  An expression before that `>`, or an apostrophe or a quote before it and an expression anywhere later, made the template throw `Solarite: bad html or duplicate attribute`.  A component's tag name mentioned in that text, in a CSS comment for instance, is also left as written; it used to get `-SOLARITE-PLACEHOLDER` appended.
- An escape sequence that JavaScript rejects inside a template, such as `"\2014"` or `"\00a0"` in the css of a `<style>`, where it has to be written `"\\2014"`, throws `Solarite: bad escape sequence in template` and shows the template.  It used to throw `Cannot read properties of undefined`.
- A list is drawn right when an element in one of its rows renders the host from its `connectedCallback` or `disconnectedCallback` as the list puts the row in or takes it out, as a tab that tells its tab set when it comes and goes does.  So is a list that holds a DOM node beside its rows when a function in a row renders the host while the list is being drawn.  The render the element or function starts draws the list, and the render that was drawing it then draws its own list once more.  Rows used to appear twice, go missing or come in the wrong order, and in 0.9.0 a list holding a DOM node could stop the page responding.
- A DOM node used as a child in a template is still shown after it moves from one expression to another inside the same parent element, such as from the first to the second of `<div>${a}|${b}</div>`, or between list rows that have no element of their own.  The place it left removed it although it already stood in its new place, and it stayed gone until the template's values changed again.  A node that one render gives to two places is shown in the one written last; it used to disappear on the next render that gave it to only one of them.
- A `DocumentFragment` given as a child, which is also what `toEl()` returns for html of several nodes, keeps showing its nodes when the same fragment is given again on the next render.  Placing its children takes them out of the fragment, so the second render found it empty and removed everything the first had shown.
- Clearing a list that is the whole content of a `DocumentFragment` takes its rows out.  They used to stay, and later renders showed them beside the new ones: in a fragment rendered into again before it was placed, and in the fragment where an element from another library keeps the children it was given until it shows them.
- A custom element that doesn't render with Solarite, such as a component from another library or one that fills a shadow root, keeps the children written inside its tag in a template.  `<fancy-button><b>Save</b></fancy-button>` used to come out as an empty `<fancy-button>`: the children, and any component declared among them, were built and then left in a placeholder that was thrown away.  The same happened to a Solarite component whose first render came later than its creation, and to the options of a `<select is="...">`, which then could not show its value.  The element may move the children it was given, all together, into its shadow root, a wrapper or another part of the page, and they are updated there.  It may not take them apart: when it replaces its content, takes out, sorts or wraps some of the nodes a `${...}` drew, or puts a node of its own between them, the next render throws ``Solarite: <fancy-button> changed the nodes ${...} drew inside it; wrap the ${...} in an element it leaves alone.``, and so does every render until the nodes are back as they were.  Nothing is drawn into nodes that are no longer where Solarite left them, and nothing is put back behind the element's back.  White space between the element's tags counts, as it does in plain html: `<fancy-button>` written with a line break before `</fancy-button>` now has a text node inside it and no longer matches `:empty`.
- A named slot takes only the children the component was given that carry its name, as the browser's own slots do.  An element with that `slot` attribute deeper down, inside one of those children, was taken out of its parent and put in the slot too, so that `<outer-card><inner-card><b slot="title">` gave the inner card's title to the outer card when both had a slot named `title`.
- A list whose rows are components defined after the list was first drawn, such as a component whose code is loaded on demand, and that holds a DOM node beside those rows, is drawn right when one of the rows changes.  The list still counted the placeholders that had stood for the components among its nodes, and put them back in the page beside the components.
- A child component's attributes whose names have a dash, such as `font-size=${15}` or `data-id="item"`, are no longer written on its element a second time without the dash, as `fontsize="15"` and `dataid="item"`.  The copies kept their first values, came back as extra arguments to `render()` on every later render, and could collide with a real attribute: `tab-index=${0}` made the component focusable.  For the same reason a two-way binding on a component, `value=${[this, 'name']}`, no longer leaves a `value` attribute holding its first value, which `assignAttributes()` called from `render()` copied back over the current one; the binding sets the property, as it does on every other element.
- A child component whose `render()` threw gets `true` from `hasChanged()` on the next render, even when its arguments are the same as on the render that threw, so a child that skips unchanged arguments draws them again.  In 0.9.0 `changed` was `false` there, and the child went on showing what it had drawn before the error.
- Attributes with expressions on a custom element tag in precompiled JSX, such as `<my-list items={rows} max-size={3}>`, reach the component under their own names and with their own types, as they do from a tagged template.  Each used to arrive as two arguments called `name` and `value`, so only the last attribute's value was passed, an array or object never arrived under its name, and a number arrived as a string.  A component written as its class, `<MyList items={rows}/>`, was not affected.
- An element that has an open shadow root of its own, such as a component whose shadow root holds only a `<slot>`, no longer goes blank the second time it renders its content with `h(this)`.  Every render emptied the element first, which removed the elements the first render had put there, and the renders after it wrote into those removed elements.  What such an element held before its first render is now kept as slot content, as it is for every other element; it used to be discarded.
- An element can be given a different template from one render to the next, such as a `render()` that shows `<p>Loading</p>` first and a list once the data has arrived.  The element used to keep the first template it was rendered with, and the values of the second were written into the places of the first: the loading message stayed for good, a list was emptied instead of replaced, text turned up in an attribute, an event handler was called as if it were content.  Usually there was no error.  After an empty template (``h(this)`` ``) the element stayed empty whatever was rendered next.  The new template now replaces what the old one put there: its elements, the attributes and handlers it put on the component itself when it is wrapped in the component's tag, its `data-id` references and its scoped style.  Attributes a parent template gave the component stay, and so do nodes other code added to the element after the old template's own.  Children the component was given for its slots move to the slots of the new template, followed by those nodes.  A component in the old template whose class wasn't defined yet is not built when the definition arrives.  An element made by `h()` or `toEl()` can be rendered into the same way, and keeps the attributes and handlers that the template that made it gave it.  An `h.selector()` whose list was in the old template no longer writes into that list's rows, and lets go of them.  The elements of the old template are discarded, so what they held (text typed into an input, the state of a child component) is not there when that template is shown again.
- A component whose template is only text, with no expression in it, keeps the children declared for it in a parent's template, after the text.  They used to be dropped.  A template with an element or an expression in it already kept them.
- A component given a child that renders the component from its own `connectedCallback` or `disconnectedCallback`, as a tab that registers with its tab set does, is drawn once.  The child's callback ran while the component's first render was moving the child into its slot, before that render had finished, so the callback's render built the template a second time in the same element and the page showed two copies, one inside the other's slot.
- An event handler is bound by the render that follows a render that threw part-way, whether the failed render was the template's first or a later one.  The next render took every handler that was the same function as before to be bound already and skipped it, so a button whose handler the failed render had not reached never responded, and a render that came back to an earlier handler left the one the failed render had given the element.

## [0.9.0] - 2026-09-19

### Added
- A `native:` prefix on an event attribute, such as `<button native:onclick=${...}>`, binds that one handler with `addEventListener` when the template renders instead of delegating it. Delegated handlers are attached when an event starts, so they run after any listener other code has added to the same element; use the prefix when that handler has to come first. It takes the same arguments, `this`, and array form as any other handler, and works in JSX as `native:onclick={...}`.
- `dist/jsx-runtime.min.js` and `dist/jsx-dev-runtime.min.js`, which import `Solarite.min.js`. A page that imports the minified build by path, as every example in the documentation does, should map `solarite/jsx-runtime` to the minified runtime; mapping it to `jsx-runtime.js` loads the unminified build as a second copy of Solarite.
- A console warning when a second copy of Solarite loads into a page, naming the address of both. Two copies don't recognise each other's templates or components, and the failures that follow give no hint of the cause. Every build shares one marker, so the source, debug, and minified builds all detect one another. This adds 73 bytes to the Brotli download.

### Changed
- **Breaking:** the `eventDelegation: 'document'` render option is gone. Passing it is harmless and just means "delegate", because what it did, keeping handlers alive on an element another component moves elsewhere in the page, now happens for every delegated handler.
- The Brotli download grew from 12.4KB to 12.7KB: mostly the reworked event dispatch described under Fixed, plus 73 bytes for the double-load warning.

### Fixed
- Delegated event handlers now behave exactly like listeners added with `addEventListener`. They used to run only once the event bubbled up to the component's root, which silently broke four things: `stopPropagation()` in a template handler could not stop a listener someone had added on an ancestor, because that listener had already run; a listener on an ancestor that stopped propagation kept the template handler from ever running; an event dispatched programmatically without `bubbles: true` never reached a handler; and an element moved out of its component lost its handlers. Solarite now attaches a real listener to each element on an event's path the moment the event starts and lets the browser dispatch normally, so ordering, `stopPropagation()`, `currentTarget`, non-bubbling events and moved elements all just work, and rendering stays as cheap as before.
- A customized built-in — a component written as `<div is="my-panel">` rather than `<my-panel>` — is now constructed once instead of twice, and one that renders from its constructor no longer nests that first render inside its own `<slot>`. The browser was upgrading the placeholder Solarite parses the template into, because an element's `is` is recorded internally and survives both removing the attribute and cloning the element; Solarite now rebuilds those elements while building the template so the placeholder stays inert. The visible symptom only appeared when rendering into an element already in the page, which is why it could pass a test and fail in the browser.
- A component declared with children inside another template no longer renders an empty `<slot>` when its own constructor builds a second component. Solarite passes those children to the new component through one shared variable, and any component created in between — typically by a field initializer, such as a toolbar that owns a menu — used to overwrite it, so the children vanished with no error and nothing in the console. The hand-off is now saved and restored around each component's construction and carries the constructor it was meant for, so an unrelated component created in the middle leaves it alone. Customized built-ins (`<div is="my-panel">`) receive their slot children correctly too.

## [0.8.0] - 2026-08-02

### Added
- **`h.selector()`** updates only the keyed rows affected by a selection change, without calling `render()` or scanning the list. Selections survive re-renders and reorders and may target a row before it exists. `when(key, on, off)` must provide a whole attribute value on the keyed row's root element.

### Changed
- **Breaking:** `h.map()` now returns an iterable `MappedList` instead of an array of templates. Embed it directly to reuse rows by item identity; spreading or nesting it still works but expands every row and loses that shortcut.
- List creation, partial updates, insertions, removals, reorders, and unchanged renders are faster. Solarite now patches only changed positions when possible, avoids unnecessary template caching and attribute work, reuses render closures, and skips unchanged event bindings.
- **Breaking:** an attribute is now removed whenever its whole-value expression is empty. `false`, `null`, `undefined`, and `''` all remove it, where previously `null` and `''` could leave `class=""` behind on an element that already had a value. Attributes an element exposes as a property, such as an `<input>`'s `value`, are unaffected: there `''` still means "empty value" and clears the field.
- The Brotli download is 9% smaller, from 13.6KB to 12.4KB.
- The production package now thows useful error messages if you use Solarite wrong. `#IFDEBUG` now contains only Solarite's internal assertions and tree validation.

### Fixed
- Valid short unquoted attributes such as `<td colspan=2>` no longer break template parsing.
- Custom elements registered under a tag other than their class's kebab-case name resolve correctly in the minified build.
- JSX projects now load one shared Solarite runtime instead of separate `solarite` and `solarite/jsx-runtime` copies.
- Functional scoped-style selectors such as `:host(:focus-within)` and dynamic plain `:host` selectors are rewritten correctly.
- The build no longer mistakes marker text in comments for an unmatched `#IFDEBUG` block.
- Clearing a form element through an expression no longer fills it with the text `false`. `<input value=${false}>` and `<input value=${undefined}>` now empty the field, because a property is cleared with a value of its own type instead of always being assigned `false`.

## [0.7.0] - 2026-07-04

### Added
- **JSX support.** Optional JSX as an alternative to `h` tagged templates, via build-time plugins for Babel, esbuild, and Vite (`babel-plugin-solarite`, `esbuild-plugin-solarite`, `vite-plugin-solarite`), plus a zero-install runtime that works with any JSX-aware toolchain. The plugins precompile to the same fast path as tagged templates; nothing here requires a build step for non-JSX users.
- `assignAttributes(el, types?, ignore?)` — reads an element's HTML attributes onto matching fields with type casting (`Number`, `Boolean`, `Date`, `String`, or a custom function), enabling plain-HTML instantiation like `<my-timer duration="7" auto-start>`.
- `getEventBinding(node, key)` — retrieve the `EventBinding` registered for a node.

### Changed
- **Breaking:** `assignFields` (and the `Cast` enum) are removed in favor of `assignAttributes`, which folds type casting into a single call.
- Event delegation is now on by default: bubbling events dispatch from one document-level listener instead of `addEventListener` per element, for much faster creation and teardown of large lists. Pass `eventDelegation: false` or an array of event names to opt out or narrow it.
- Tighter terser compress options for a smaller minified bundle.

## [0.6.0]

### Added
- **Keyed lists.** A reserved `key=${expr}` attribute makes DOM node identity follow the data across re-renders, using a two-pointer prefix/suffix scan plus a longest-increasing-subsequence pass for minimal node moves. Passes the official krausest keyed checks.
- `h.map` (replacing `h.memo`) for efficient identity-based list rendering — a ~2% benchmark gain (score 1.10 → 1.08).
- Two-way binding for radio buttons.

### Changed
- Playgrounds in the docs lazy-load below the scroll margin for faster page load.
- Smaller bundle: removed `udomdiff` and `getArg.js`.
